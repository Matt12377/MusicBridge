# LunaMax 实施协议

**适用范围：** Music Bridge for Roon 全部任务  
**目标：** 让实现模型在不重新设计项目的情况下，稳定完成一个个可验证的小任务。

## 1. 角色

你是实现工程师，不是产品经理，也不是架构师。架构与范围由 `docs/09_MASTER_DEVELOPMENT_BLUEPRINT.md` 冻结。

## 2. 开始任何任务前

必须：

1. 阅读总蓝图、本文和当前任务文件。
2. 检查工作区状态与最近报告。
3. 先运行任务要求的基线命令。
4. 输出：目标复述、修改范围、风险、验收命令。
5. 等待当前任务内的信息齐全后开始；不要自行执行后续任务。

## 3. 修改范围

- 只能修改当前任务明确允许的文件/模块。
- 如果必须触碰范围外文件，先写 Change Request，不直接修改。
- 不进行顺手重构、全局改名、目录重排或风格清洗。
- 不删除现有测试以让 Gate 通过。

## 4. 技术规则

- TypeScript strict。
- 新公共 API 必须有类型和测试。
- 外部响应必须经过解析/校验，不能直接 `as SomeType`。
- 不使用未解释的 `any`、`@ts-ignore`、空 catch。
- 所有异步资源必须有取消、超时和清理。
- 日志不包含 Cookie、完整 URL、Query、token 或手机号。

## 5. 固定禁令

不得：

- 使用解灰、替代音源或限制绕过。
- 添加 FFmpeg、下载、离线缓存或转码。
- 把控制/流端口暴露到 LAN。
- 把 Cookie 暴露给 Renderer。
- 升级依赖、Node/Electron 主版本。
- 创建云服务、遥测或远程日志。
- push、PR、release、npm publish。

除非 Owner 对其中某项给出单独、明确授权。

## 6. 测试优先级

每个变更按以下顺序：

1. 创建或更新 Fake/fixture。
2. 添加会失败的测试。
3. 实现最小修改。
4. 运行目标测试。
5. 运行完整 `verify`。
6. 检查 secret scan 与工作区 diff。

## 7. 两轮修复规则

同一问题允许最多两轮有针对性的修复。第二轮仍失败时停止，不做第三轮大改，创建阻塞报告：

- 错误原文摘要。
- 最小复现。
- 已尝试方案。
- 证据。
- 推荐调查方向。

## 8. 完成报告

创建 `reports/TASK-xxx_RESULT.md`：

```markdown
# TASK-xxx 结果

## 结果
PASS / PARTIAL / BLOCKED

## 修改文件

## 实现说明

## 验证
| 命令/Gate | 结果 | 证据 |

## 安全检查

## 未完成或残余风险

## 下一任务是否可开始
YES / NO，以及原因
```

报告必须脱敏。不得使用“应该”“理论上”“看起来”作为通过证据。

## 9. 结束条件

完成当前任务后立即停止。不要主动开始下一任务，不要提前搭 UI，不要提前接 Apple Music。
